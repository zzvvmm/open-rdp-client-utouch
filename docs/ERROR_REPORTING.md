# Error reporting

**Settings → Report Errors** is enabled by default. Turning it off stops new
reports immediately and persists the preference in the application's existing
settings file. Existing preferences are preserved when updating from an older
version. A report already accepted for sending may finish after the switch is
turned off. Reports use an in-memory queue; no offline report files are stored.

## Projects and configuration

Organization: `dd-0q`, team: `dd`.

| Project | Captures |
| --- | --- |
| [open-rdp-client-utouch-backend](https://dd-0q.sentry.io/settings/projects/open-rdp-client-utouch-backend/) | Rust panics and unexpected RDP failures |
| [open-rdp-client-utouch-ui](https://dd-0q.sentry.io/settings/projects/open-rdp-client-utouch-ui/) | QML reference/type/binding/load errors and Qt critical/fatal messages |

The public client DSNs are in [`sentry.json`](../sentry.json), embedded in the
Rust backend at build time. These keys allow event submission; they are not
account/API authentication tokens. No Sentry auth token is required on a phone.
Never put a Sentry account token in that file or in the application package.

The integration uses the official Sentry Rust SDK with Rustls and the same Ring
provider as IronRDP, without an OpenSSL dependency. Qt forwards only an allowlisted
error category and source location to Rust. The two clients share the same
atomic reporting preference, so backend and UI reporting switch together.

Release is `rdp-client-ut@VERSION`, taken from Cargo's package version. Debug builds
use `development`; release builds use `production`. The DSNs and version are
compiled into both architecture packages, so end users need no environment setup.
Publishing the next release follows [RELEASING.md](RELEASING.md); project setup
does not publish a new application version.

## Data and limits

Events contain an allowlisted error type/summary, release, environment,
architecture, application framework, component, and safe source locations.
Panic payloads and raw RDP/Qt messages are never sent. The SDK callback rebuilds
each event, removing user/account details, PC addresses, screen contents,
clipboard text, logs/breadcrumbs, source context, absolute paths, and local
variable values. Only QML files shipped as application resources are accepted.
Sentry receives the sending network's public IP as part of the HTTPS connection
and can derive coarse location server-side. No persistent user/device identifier
is generated by this integration.

Offline PCs, DNS/TCP failures, connection timeouts, rejected certificates, invalid
input, and ordinary authentication failures are not reported. Unexpected RDP
session/decoder, negotiation, and TLS errors are reported using fixed summaries.
Reports are limited to one per error type/source location per minute, with a
bounded set of 128 locations per process and bounded SDK queues.

Rust panics and Qt fatal log messages get a bounded flush before termination.
Native faults such as `SIGSEGV`, C++ process termination without a Qt message,
and operating-system kills do not pass through these hooks. Native crash dumps,
session replay, performance traces, and general log collection are not enabled.

Rust panic file/line and QML resource file/line are retained even when packages
are stripped. A debug build also includes resolved application function names.
Complete native stack traces in stripped production binaries would require
separate debug artifacts and a symbol-upload pipeline; that is not configured by
this error-only integration. Source code/context and native memory dumps are not
uploaded.

## Verification

Run the normal unit and QML checks:

```bash
cargo test --locked
clickable test --arch amd64 --non-interactive
```

For an explicit backend delivery check, use isolated data so it does not change
personal settings or saved PCs:

```bash
RDP_CHECK_DIR=$(mktemp -d)
XDG_CONFIG_HOME="$RDP_CHECK_DIR/config" \
XDG_CACHE_HOME="$RDP_CHECK_DIR/cache" \
XDG_DATA_HOME="$RDP_CHECK_DIR/data" \
cargo run --locked --bin rdp-client-ut-cli -- --sentry-check
```

This developer-only CLI catches a deliberate panic after initializing the same
controller/reporter used by the Qt application. It is not included as a button
or trigger in the shipped Qt app. If the current data directory has reporting
disabled, the command refuses to send. A successful flush alone does not prove
ingestion; confirm the new event in the selected Sentry project.

The initial setup confirmed these deliberate verification issues:

- [RustPanic: Unexpected Rust panic](https://dd-0q.sentry.io/issues/OPEN-RDP-CLIENT-UTOUCH-BACKEND-1), with application function names and `src/main.rs` source location in a debug build.
- [QmlReferenceError: A QML reference could not be resolved](https://dd-0q.sentry.io/issues/OPEN-RDP-CLIENT-UTOUCH-UI-1), with `qml/Main.qml:2` from a native release build using the real Qt message handler.

The native check first disabled reporting and caused a real QML `TypeError`, then
enabled reporting and caused a `ReferenceError`. Only the enabled report appeared
in Sentry. Temporary native verification fixtures and screenshots are under
ignored `build/`; they are not packaged. The verification issues are left
available for inspection and can be resolved manually.

Reference: [Sentry Rust SDK](https://docs.sentry.io/platforms/rust/),
[Rust native crash-reporting scope](https://docs.sentry.io/platforms/rust/native-crash-reporting/).
